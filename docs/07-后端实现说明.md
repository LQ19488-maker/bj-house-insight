## 1. 目录与职责

```
backend/
├── server.py              入口：装配中间件链 + 路由表 + 静态托管
├── httpkit/               手写框架层（与业务无关，可整体替换）
│   ├── router.py          正则路由 + 路径参数 + 鉴权标注
│   ├── ctx.py             请求上下文（handler 唯一接触的对象）
│   ├── response.py        统一响应体 + 12 个错误码
│   ├── middleware.py      RequestID / Logger / CORS / Auth / Recovery
│   ├── multipart.py       手写 multipart 解析（cgi 已在 3.13 移除）
│   └── static.py          静态托管 + SPA 回退（替代 Nginx try_files）
├── api/handler/           第 1 层：绑定参数 → 调 service → 返回 data
├── service/               第 2 层：业务规则（口径、降级、阈值、置信度）
├── repository/            第 3 层：只有 SQL 与参数绑定
├── model/entities.py      行 → dataclass，唯一的实体转换点
├── dto/                   params.py（校验）/ views.py（契约字段名）
└── core/                  config / db / security（PBKDF2 + JWT）
```

依赖方向单向：`handler → service → repository → core.db`，禁止反向。
**`tools/check_layers.py` 自动检查，8 项全绿**（替代手册要求的"人工抽查 handler 有没有 SQL"）。

## 2. 中间件链

本项目的"中间件"是显式编排的函数序列，不依赖框架钩子：

```
请求 → RequestID → 读 body(限长) → 路由匹配 → Auth(按路由级别) → handler
                                                              ↓
                     Recovery(转错误码) ← Logger(JSON 到 stdout)
```

| 中间件 | 行为 |
|---|---|
| RequestID | 8 位 uuid，写入响应体与日志，便于排障 |
| Logger | 单行 JSON → stdout；`took_ms > 500` 追加一条 WARN |
| CORS | 允许 `GET/POST/DELETE/OPTIONS`，回显 Origin |
| Auth | `public` / `optional` / `login` / `admin` 四档，由路由表声明 |
| Recovery | 未捕获异常统一转 `5000`，**不把堆栈吐给客户端**，只在服务端 stderr 留痕 |

## 4. 鉴权：用标准库复刻 bcrypt 与 JWT

| 需求 | 手册方案 | 本项目实现 | 说明 |
|---|---|---|---|
| 密码哈希 | bcrypt(cost=10) | `pbkdf2_hmac('sha256', pwd, salt, 200_000)` | NIST SP 800-132 推荐，stdlib 内置 |
| 令牌 | PyJWT | HS256 手写（`hmac` + `base64url`） | HS256 本质就是 HMAC-SHA256 |
| 失败锁定 | Redis 或内存 | 进程内计数，5 次锁 15 分钟 | **单机局限已写入 ADR §11** |
| 角色控制 | `RoleRequired("admin")` | 路由表声明 `auth=ADMIN` | 越权返回 `2003`，不是 500 |

> 一处刻意的设计：**登录不校验密码强度**，只有注册校验（8–64 位）。
> 否则历史上用短密码创建的账号将永远无法登录——这是实现时被冒烟测试抓出来的真实 bug。

## 5. 数据访问的五个关键决定

1. **`build_filter()` 被列表与 COUNT 共用** —— 直接堵掉"共 2890 条但翻到第 2 页就空"的经典 bug。
   冒烟测试里有专门一条断言：加了筛选条件后，`page=1` 与 `page=2` 的 `total` 必须相同。
2. **排序白名单** —— `sort` 只接受 5 个字段名，映射到列名后再拼 SQL；`?sort=drop%20table` 返回 `1002`。
3. **PRAGMA 三件套** —— `foreign_keys=ON`（SQLite 默认不校验外键）、`journal_mode=WAL`、
   `busy_timeout=5000`。
4. **每请求一个连接** —— `ThreadingHTTPServer` 多线程，连接不跨线程共享。
5. **中位数与分位** —— SQLite 没有 `median()`，用 `ORDER BY ... LIMIT 2 OFFSET (n-1)/2` 取中间两值；
   相关系数用一条聚合 SQL 算（`Σx, Σy, Σxy, Σx², Σy²`），不把全表拉到应用层。

## 6. 静态托管与 SPA 回退

非 `/api/v1` 的 GET 请求：

```
dist/ 下有该文件 → 直接返回（正确的 content-type）
dist/ 下没有     → 返回 index.html（200，不是 404）→ 刷新 /analytics 不会 404
dist/ 整体不存在 → 返回 404 + 提示"请先 npm run build"
```

路径 `resolve()` 后必须仍在 `dist/` 内，防 `../` 穿越。这样可以**不用 Nginx** 单进程单端口部署。

## 7. 导入接口复用 ETL（架构上最关键的一点）

```
POST /admin/import
  → handler：手写 multipart 解析（cgi 已移除）+ 扩展名/大小校验
  → service.admin_service.import_excel：
        etl.read → etl.clean(R1–R12) → etl.validate（与命令行同一份代码）
        → 维度 upsert → house / house_orientation / data_quality_issue
        → 刷新三级维度聚合快照
  → 返回质量报告（行数漏斗 / 规则触发统计 / 断言结果）
```

好处是结构性的：

- 命令行 ETL 与接口导入**不是两套逻辑**，不存在"对不齐"的可能
- `dry_run=true` 天然成立——同一条链路只差最后是否写库
- 冒烟测试实测：`dry_run` 报告 `loaded_rows=2890 / rejected_rows=0`，**质量断言全部通过**

代价要说明：导入路径需要 pandas + openpyxl（已在 `.venv` 中），**纯查询功能不需要**。

## 9. 已知局限（与 ADR §11 对应）

| 局限 | 影响 | 缓解 |
|---|---|---|
| 失败锁定用进程内字典 | 多进程/重启后计数丢失 | 单机部署；ADR 已写明换 Redis 的路径 |
| 每请求 `Connection: close` | 放弃 keep-alive | 单请求 <10 ms，开销可忽略，换来连接稳定性 |
| 无 gunicorn/uvicorn | 无进程管理与优雅重启 | PaaS 侧由平台托管；本机演示无影响 |
| 导入依赖 pandas | 纯查询功能不受影响 | 延迟 import，缺依赖时返回明确错误 |
| JWT 密钥缺省时临时生成 | 重启后旧 token 失效 | 启动日志明确提示；生产必须设 `JWT_SECRET` |
