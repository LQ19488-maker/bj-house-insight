## 1. 模块总览

| 编号 | 模块 | 一句话职责 | 边界：做什么 | 边界：明确不做 | MoSCoW | 优先级理由 |
|---|---|---|---|---|---|---|
| M1 | 数据接入与治理 | 把 Excel 变成可信、可追溯的入库数据 | 导入、dry-run、清洗留痕、质量报告、批次记录 | 不负责分析展示；不做数据编辑（只做整批导入，不提供单行修改） | **Must** | 一切数据的地基，且是评分 15% 的正面观测点 |
| M2 | 房源检索 | 按多条件找到目标房源 | 11 类筛选、排序、分页、筛选字典 | 不做分析统计（统计归 M4）；不缓存结果集 | **Must** | Q11 是最高频用户动作，也是 M3/M6 的入口 |
| M3 | 房源详情与对比 | 判断单套房"贵不贵"、多套"怎么选" | 详情、单价分位、相似房源、四房对比、雷达归一化 | 不做跨房源统计分析；不提供估价（归 M6） | **Must** | 分位与相似房源是对比的核心，直接回答 Q12 |
| M4 | 市场分析看板 | 用图回答"价格由什么解释" | 区级汇总、分布、散点、房龄趋势、分区对照、溢价双口径、楼层朝向、全局联动 | 不做明细列表；不做导出（归 M7） | **Must** | 评分 15% 的正面观测点，且是论文/答辩的核心论据 |
| M5 | 小区画像 | 刻画单个小区与街道的相对水平 | 小区聚合、在售表、同街道分位、街道排行（排除伪街道） | 不做小区级波动分析（67.4% 小区仅 1 套）；不做跨街道对比总览 | Should | 数据粒度受限，价值集中在"位置感"而非"波动" |
| M6 | 估价参考 | 给定条件给出可解释的参考价 | 入参校验、相似样本召回、加权均价、降级链与置信度、免责说明 | 不承诺精度；不做深度学习模型；不替代评估报告 | Should | 亮点功能但非演示必需，且必须严格限定方法论 |
| M7 | 收藏与导出 | 把结果带出系统 | 收藏/取消（幂等）、收藏列表、对比篮持久化、CSV/PNG 导出 | 不做分享链接的短链服务；不做 Excel 导出（用 CSV） | Could | 便利性功能，缺失不影响核心闭环 |
| M8 | 系统管理 | 认证、权限、审计、健康检查 | 注册/登录/锁定、JWT、角色控制、操作日志、健康检查 | 不做用户管理后台（增删改用户）；不做多租户 | **Must** | `/health` 与鉴权是工程可运行性的底线 |

**Must 模块 5 个**（M1、M2、M3、M4、M8），符合"Must ≤ 5"约束。

### 1.1 两两重叠检查结论

逐对检查 8 个模块的 28 组组合，结论：

| 潜在重叠点 | 检查结论 |
|---|---|
| M2 检索 vs M4 看板 | 不重叠：M2 返回**明细列表**，M4 返回**聚合结果**；M4 的全局筛选只改变聚合范围，不返回明细 |
| M3 相似房源 vs M6 估价 | 共用同一个 `recall_similar()` 召回函数（在 M6 中声明依赖），但 M3 输出**房源列表**，M6 输出**价格区间**，职责不同 |
| M5 街道排行 vs M4 区级汇总 | 不重叠：粒度不同（街道 vs 区），且 M5 排除伪街道、带样本阈值，M4 全量展示并标注 n |
| M2 筛选字典 vs M1 数据治理 | 不重叠：M2 只读维度表，M1 只写 |
| M7 导出 vs M4/M5 | 不重叠：M7 只消费已渲染结果，不产生任何指标 |
| M8 认证 vs 所有模块 | 不重叠：M8 提供横切能力（中间件），不承载业务规则 |
| M1 质量报告 vs M8 操作日志 | 不重叠：前者是**数据问题**（R1–R12），后者是**用户行为**（登录/导入） |

**结论：任意两个模块之间不存在功能点重复。**

## 3. 模块依赖与数据流

### 3.1 依赖表

| 模块 | 依赖模块 | 依赖内容 |
|---|---|---|
| M1 | —（仅依赖 ETL 包） | 复用 `etl.clean` / `etl.validate`，与命令行同一份规则 |
| M2 | M1 | 已清洗的 `house` 与维度表；`is_pseudo` 过滤 |
| M3 | M2 | 检索条件构造器（复用 `build_filter`）；相似房源召回 |
| M4 | M1 | `district`/`street`/`community` 聚合快照 + `house` 明细 |
| M5 | M1、M4 | 聚合结果口径（均价/中位单价定义必须与 M4 一致） |
| M6 | M1、M3 | 相似房源召回函数、面积/房龄筛选口径 |
| M7 | M2、M3、M4 | 检索结果、对比篮、图表配置 |
| M8 | —（横切） | 为全部模块提供鉴权中间件与日志 |

> 依赖图为有向无环图（DAG），**无环**。M8 作为横切能力不参与环判定。

### 3.2 三条关键数据流

**数据流 1：管理员导入数据**

```
上传 xlsx(M8 鉴权) → M1 文件校验 → M1 复用 etl.clean+validate(R1–R12)
  → 落 import_batch + data_quality_issue → 写 house / house_orientation
  → 刷新 district/street/community 聚合快照 → 返回质量摘要
```
落地表：`import_batch`、`data_quality_issue`、`house`、`house_orientation`、`district`、`street`、`community`

**数据流 2：用户检索到详情**

```
M2 组合筛选(11 类条件) → build_filter() → house + 维度返回 HouseCard
  → 点击进入 M3 详情 → 同区单价分位 + 相似房源(小区→街道→区降级)
  → 加入对比篮 → M3 属性矩阵 + 雷达五维
```
落地表（只读）：`house`、`house_orientation`、`community`、`district`、`street`

**数据流 3：分析看板出图**

```
M4 全局筛选(区/房龄段/面积段) → 并发请求 7 个聚合接口
  → district 快照 + house 聚合 → 双口径溢价(全市/同区)
  → 前端每张图做数值断言(分组合计 = 接口合计) → 渲染 SVG
  → M7 导出 PNG(含口径说明)
```
落地表（只读）：`district`、`street`、`house`、`house_orientation`

## 4. MoSCoW 与最小可演示闭环

| 优先级 | 模块 | 说明 |
|---|---|---|
| Must | M1、M2、M3、M4、M8 | 缺任一个都无法完成一次完整演示 |
| Should | M5、M6 | 显著提升说服力，缺失不影响主流程 |
| Could | M7 | 便利性功能 |
| Won't（本期） | — | 见 SRS 第 7 章"本期不做清单" |

### 最小可演示闭环（3 天可跑通）

**模块**：M1（seed 导入）+ M2（检索）+ M3（详情）+ M4（看板）+ M8（health）
**页面**：P1 市场概览 → P2 房源检索 → P3 房源详情
**闭环动作**：`run-etl.cmd --db` 建库 → 打开概览看到 2890 条与 17 区均价 → 进入检索按"朝阳 + 400–600 万 + 近地铁"筛出结果 → 点进详情看到该房在西城的单价分位 → 返回看板看分区房龄对照图。

## 5. 开发顺序（4 个迭代批次）

| 批次 | 模块 | 可交付物 | 依赖前置 | 可并行 |
|---|---|---|---|---|
| **迭代 1：数据与骨架** | M1、M8 | ETL 产物（已完成）、SQLite 库（已完成）、`/health`、鉴权中间件、统一响应体、三层目录 | 批 2 建表已完成 | M1 与 M8 可并行 |
| **迭代 2：检索与详情** | M2、M3 | 7 个查询/详情接口、`HouseCard`/`HouseDetail` DTO、单价分位、相似房源降级链 | 迭代 1 | M2 与 M3 可并行（M3 复用 M2 的 filter 构造器） |
| **迭代 3：分析看板** | M4 | 8 个聚合接口、双口径溢价、分区房龄对照 | 迭代 1 | **与迭代 2 完全并行**（只读、互不阻塞） |
| **迭代 4：画像估价导出** | M5、M6、M7 | 小区画像、估价与降级链、收藏幂等、CSV/PNG 导出 | 迭代 2（M6 复用召回） | M5 与 M6 可并行；M7 最后做 |

**并行分工建议**（供多人协作）：迭代 3 与迭代 2 无共享写路径，两人可同时开工；一人在 M4 写聚合 SQL，一人在 M2/M3 写列表与详情，接口契约以 `docs/api-contract.md` 为准。
