## 1. 路由表

| 路径 | 组件 | 分组 | 说明 |
|---|---|---|---|
| `/overview` | OverviewView | 分析 | 4 KPI + 区均价 + 分布 + 热门小区 |
| `/analytics` | AnalyticsView | 分析 | 8 张图（含 2 张同区控制对照） |
| `/search` | SearchView | 找房 | 11 类筛选 + 排序 + 分页 |
| `/houses/:id` | DetailView | 找房 | 属性 + 分位标尺 + 相似房源 |
| `/compare` | CompareView | 找房 | 最多 4 套属性矩阵 + 雷达 |
| `/communities/:id` | CommunityView | 辅助 | 同街道位置 + 排行 |
| `/valuation` | ValuationView | 辅助 | 9 项入参 + 结果卡 |
| `/admin` | AdminView | 管理 | 导入/批次（接口模式）· 质量报告（静态模式） |
| `/` 与未匹配 | — | — | 重定向到 `/overview` |

**采用 hash 路由**（`createWebHashHistory`）：GitHub Pages 没有 `try_files`，
history 模式下刷新 `/analytics` 会 404。hash 模式下 URL 形如 `/#/analytics`，刷新与分享都不受影响，
且与用户既有项目的路由习惯一致。

### 1.1 「所有可点入口都必须有内容」

侧栏**只放一定会有内容的入口**。需要具体 id 的页面（房源详情、小区画像）不做硬编码入口
（早期版本曾写过 `/houses/1`、`/communities/1`，点了没有上下文，已移除），改为从真实数据进入：

| 目标页 | 怎么进 |
|---|---|
| 房源详情 `/houses/:id` | 概览/检索的结果行点击、相似房源行点击、小区画像的在售表 |
| 小区画像 `/communities/:id` | 概览页的"查看画像"按钮 |

另外两道保险：

1. **`tools/check_links.py`** —— 解析路由表，扫描源码里全部 13 个跳转目标（含模板字符串与 NAV 数组），
   校验"每个跳转都命中路由"且"每个路由都有入口"，并禁止侧栏出现硬编码 id。
2. **`frontend/public/404.html`** —— GitHub Pages 对未知路径返回该页，
   自动把访问者送回应用入口（相对路径，换仓库名不用改）。因此旧的原型链接
   （如 `p3-detail.html`）不会再显示 GitHub 的 404，而是自动跳回首页。

## 2. 组件树

```
App.vue
└── AppLayout.vue               顶栏（导航 + 数据源模式指示）+ 侧栏（分组菜单）+ 内容区 + 页脚
    └── <RouterView>
        ├── PageHeader.vue      标题 + 副标题 + 口径说明
        ├── StatCard.vue        KPI/指标卡（label / value / unit / field / desc）
        ├── ChartCard.vue       图表卡（标题 + 口径 tooltip + 加载/空/错误三态 + 导出 PNG）
        └── 8 个 View
            ├── OverviewView     2× ChartCard + 4× StatCard + 小区卡
            ├── AnalyticsView    8× ChartCard
            ├── SearchView       左侧筛选面板 + el-table + el-pagination
            ├── DetailView       el-descriptions + 1× ChartCard + 相似房源表
            ├── CompareView      el-table（差异高亮）+ 1× ChartCard(雷达)
            ├── CommunityView    4× StatCard + 2× ChartCard + 2× el-table
            ├── ValuationView    el-form + el-descriptions 结果卡
            └── AdminView        el-upload/el-table/el-descriptions（两种模式分支）
```

三个基础组件（`PageHeader` / `StatCard` / `ChartCard`）解决了两件容易做漏的事：

- **口径说明只写一次**：`ChartCard` 的"口径"气泡与图注绑定同一个 `caliber` 字段；
- **三态不漏**：`ChartCard` 内建 loading / empty / error（带重试），每个图表天然具备，
  不需要在 8 个页面里各写一遍。

图表 option 全部由 `src/charts/options.js` 的**纯函数**生成（9 个构造函数），
页面只负责取数，不碰 ECharts 配置。

## 3. 状态管理设计

判据：**跨路由存活 或 多处写入 或 需要同步到 URL** 才进 Pinia。

| Store | 内容 | 为什么进 store |
|---|---|---|
| `useFiltersStore` | 检索页 18 个字段（含 sort/order/page） | 详情页返回检索要还原现场；且需与 URL 双向同步 |
| `useCompareStore` | 对比篮（最多 4 条，`sessionStorage` 持久化） | 详情页"加入" → 对比页"读取"，跨路由 |

**不进 store 的**：抽屉开合、图表 hover、加载态、分页游标——纯页面局部状态，
进 store 只会污染全局。`useUrlSync()` 组合式函数负责筛选条件的双向同步
（状态变化 → `router.replace({query})`；URL 变化 → 回填状态）。

## 4. 数据层：一套页面，两种数据源

这是本阶段最重要的架构决定——为了让同一套页面既能跑**本地完整系统**，
又能上 **GitHub Pages 只读站**。

```
        src/api/index.js  ← 页面唯一的数据入口（VITE_DATA_SOURCE 决定用哪个实现）
              ├── httpSource.js    调 /api/v1/*（30 个接口）
              └── staticSource.js  读 public/data/*.json，在浏览器内存里计算
```

| 项 | httpSource | staticSource |
|---|---|---|
| 数据来源 | 后端 REST 接口 | `houses.json`（93 KB gzip）+ `meta.json` + `quality.json` |
| 检索/排序/分页 | SQL + 索引 | 内存 `filter/sort/slice` |
| 分位/中位/相关系数 | SQL 聚合 | JS 计算（同口径） |
| 估价 | 后端加权均价 | 前端同一算法 |
| 可用能力 | 全部（含登录/收藏/导入） | 只读分析（P8 降级为质量报告展示） |

**关键约束**：两份实现必须返回**完全相同的数据结构**。
这一点不能靠人工保证，因此写了 `tools/check_parity.py`：
启动后端，用 Node 同时调用两套实现，逐字段比对 **21 组请求**。
当前 **21/21 通过**（详细结果见本文 §7）。

## 5. 图表清单

| 图 | 函数 | 用的 ECharts 能力 |
|---|---|---|
| 区均价 Top10 | `districtBarOption` | bar（横向）+ 样本量标签 |
| 总价分布 | `histogramOption` | bar + 分位分桶 |
| 面积–总价散点 | `scatterOption` | scatter + line（回归线）+ graphic 标注 r |
| 房龄–单价（全市） | `ageLineOption` | line + areaStyle + markLine（均值） |
| 房龄–单价（分区） | `ageLineOption({multi})` | 多 line 序列 + `connectNulls:false` |
| 溢价（全市 / 同区） | `premiumBarOption` | bar + markLine（全市基准线） |
| 户型构成 | `donutOption` | pie（环） + scroll legend |
| 楼层 / 朝向 | `groupBarOption` | bar（横向）+ 样本不足降透明度 |
| 对比雷达 | `radarOption` | radar + 多序列面积叠加 |
| 单价分位标尺 | `quantileOption` | 双 bar 堆叠（区间）+ scatter（本房）+ markLine（中位） |

按需注册：`bar/line/pie/radar/scatter` + `grid/tooltip/legend/title/markLine/dataZoom`，

## 6. 构建与体积

| 产物 | 原始 | gzip |
|---|---|---|
| `echarts` chunk | 637 KB | 218 KB |
| `index` chunk（Vue + Router + Pinia） | 138 KB | 55 KB |
| Element Plus 按需分包（el-table 92 KB / el-popper 125 KB / …） | ≈ 420 KB | ≈ 130 KB |
| CSS 合计 | ≈ 12 KB | ≈ 5 KB |
| 静态数据 `data/*.json` | 405 KB | 102 KB |
| **合计** | **1.68 MB** | **548 KB** |

**关键优化**：Element Plus 从全量引入改成按需引入（`unplugin-vue-components` +
`ElementPlusResolver`），dist 从 **2.45 MB → 1.68 MB**，跨过手册"dist < 2 MB"的验收线。

## 7. 联调问题记录（6 条真实问题及解决）

| # | 问题 | 现象 | 根因 | 解决 |
|---|---|---|---|---|
| 1 | `npm install` 失败 | `EPERM spawn` | 沙箱禁止 npm 通过管道捕获子进程输出（esbuild postinstall 触发） | 用 `--ignore-scripts` 安装；esbuild 二进制由 `@esbuild/win32-x64` 提供，无需 postinstall |
| 2 | `vite build` 失败 | `spawn EPERM` | esbuild 必须启动子进程走管道协议 | 提权执行构建（记录在案：这是环境限制，不是代码问题） |
| 3 | 构建报顶层 await | `Top-level await is not available in ... es2020` | `api/index.js` 用 `await import()` 按需加载数据源 | 改为静态 import + 运行时选择实现（两份实现合计 < 20 KB，不值得改 target） |
| 4 | dist 超 2 MB | 2.45 MB，卡在验收线上 | Element Plus 全量引入（1.0 MB JS + 365 KB CSS） | 改按需引入，降至 1.68 MB |
| 5 | 冒烟测试"静态未构建 → 404"失败 | 该路径返回 200 HTML | dist 已构建，后端按 SPA 回退返回 index.html | **不是 bug，是功能生效**；测试改为验证 SPA 回退与静态数据可达 |
| 6 | 静态/接口数字分叉 | 6 处不一致 | 两份实现口径细节不同 | 逐项修复，见下表 |

### 7.1 双模式一致性检查抓出的 6 处分叉

| 分叉 | 具体差异 | 修复 |
|---|---|---|
| 散点抽样点数 | 接口 500 点 / 静态 482 点 | 静态改用与后端相同的 `step = floor(n/limit)` |
| 溢价 by_district 顺序 | 后端按区内套数降序，静态按 district_id 升序 | 静态改为按 house_count 降序 |
| 小区画像 street_rank 字段 | 静态多返回 6 个字段 | 静态裁剪为与契约一致的 5 个字段 |
| 街道排行 excluded 计数 | 前端 74 / 后端 1764 | **后端 bug**：查街道时汇报的是"被排除的小区数"；改为按 scope 分别统计 |
| 小区排行同值顺序 | `house_count` 相同时顺序不同 | 静态补 `id` 次级排序键，与后端 `ORDER BY ..., id` 一致 |
| 区级汇总返回结构 | 测试脚本漏取 `.list` | 修测试（非业务代码） |

## 9. 已知局限

| 局限 | 说明 |
|---|---|
| 静态模式无登录/收藏/导入 | GitHub Pages 无服务端状态；P8 降级为质量报告只读展示，菜单标注"静态模式（只读）" |
| 静态模式首次加载需下载 93 KB 数据 | 随后所有筛选/聚合都在内存完成，无需再请求；相比逐次打接口反而更快 |
| 未做虚拟滚动 | 2890 条数据靠分页（20/50/100）即可，虚拟滚动属过度优化 |
| 未做移动端适配 | 手册要求桌面优先（≥1366×768），1280 以下收侧栏；窄屏可用但非目标场景 |
| 无端到端浏览器测试 | 环境无浏览器，改为"构建通过 + 双模式一致性 + 后端冒烟"三重替代验证 |
