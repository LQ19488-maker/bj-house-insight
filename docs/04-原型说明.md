## 3. 首页 4 个 KPI 与真实统计的一致性

| KPI | 原型显示 | 真实统计 | 口径 |
|---|---|---|---|
| 在售房源数 | 2890 | 2890 | `COUNT(*) FROM house` |
| 全市均价 | 64,764.78 | 64,764.78 | **算术均值**；面积加权为 64,028.12 |
| 中位总价 | 470 万 | 470 万 | 线性插值中位数 |
| 覆盖小区 | 1865 | 1865 | (区,小区) 组合；名称去重为 1864 |

> 手册要求首页 KPI 为 2890 / 64765 / 470 / 1864。其中小区数取 **1865**（组合数），因为按 `(district, name)` 建表实际是 1865 行——绿地中央广场跨昌平/通州。此处与手册的 1864 属于同一类订正，详见 `docs/00-数据事实卡-v2.md §9`。

## 4. 全局交互规则

| 状态 | 规则 |
|---|---|
| 加载态 | 图表区显示骨架屏；列表显示 5 行占位；并发请求用 `Promise.allSettled`，单图失败不阻塞其余 |
| 空状态 | "该条件下无房源，试试放宽价格区间" + 一键清空筛选按钮 |
| 错误态 | "服务异常，请稍后重试" + 重试按钮 + `request_id`（便于排障） |
| 样本不足 | 任何分组 `n < 3` 时显示"样本不足"角标，不画柱 |
| 极值行 | 用浅橙点/角标提示"已标记极值"，**不隐藏** |
| 口径说明 | 每张图右上角 tooltip 展示指标定义 + 单位 + n + 是否含极值 |

## 5. 设计决策

**为什么筛选放左侧？** 检索是"条件优先"的任务：用户先想清楚预算与区位，再看结果。左侧竖排面板可以容纳 11 个控件而不挤压结果区，且与后台系统的操作习惯一致。

**为什么 KPI 用 4 个？** 这四个数分别回答"市场有多大（2890）／多贵（均价）／典型价位（中位总价）／多分散（小区数）"，再多就会稀释注意力。

**信息层级怎么划？** 概览页只给结论性数字与两张图；看板页才展开"为什么"；详情/对比/估价页面向单个决策。三级层级对应三种阅读速度。

**为什么不用箱线图画小区？** 67.4% 的小区只有 1 套在售，箱线图会画出一堆单点。改用点图 + 参照线表达"在同街道中的位置"。
